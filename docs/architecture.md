# AGOS Proxy Architecture

> Internal design reference. Covers the mental model, crate layout, data model,
> request lifecycle, health subsystem, routing strategies, streaming behavior,
> and the build roadmap.

## Mental model

AGOS Proxy is a self-hosted AI gateway. From the caller's point of view it is a
single OpenAI-compatible provider; underneath, it fans requests out across
configured LLM providers with automatic failover.

Two parallel hierarchies share a common top-level tenant, the **Profile**:

```
Profile ("coder1")
│
├── Providers                     how we reach the outside world
│     ├── Deepseek        base_url, auth_token
│     ├── Claude          base_url, auth_token
│     └── Google AI Studio base_url, auth_token
│
└── Proxies                      what the outside world is allowed to ask for
      └── Proxy: "Programmer"
            ├── Route: "php-developer-3.5-flash"
            │     1. deepseek-v4-flash        (Deepseek)
            │     2. glm-5.3-flash            (OpenRouter)
            │     3. gemini-3.5-pro           (Google)
            │     4. claude-sonnet-5          (Claude)
            │
            └── Route: "flutter-expert-2-preview"
                  1. ...
```

- **Provider** = *how* a call is made (credentials + base URL + provider kind).
- **Proxy / Route** = *what* callers may request.
- A **route never exposes a single model** — it exposes an *ordered fallback
  chain* of models, each pointing at one configured provider.

This split is the whole point: the caller configures a route name once
(`Programmer/php-developer-3.5-flash`) and never sees Deepseek, Claude or
Gemini directly. Everything behind that name can change (models swapped,
providers added or removed) without the caller's configuration changing.

## Crate layout

```
src/
├── lib.rs           crate root, module wiring, VERSION
├── main.rs          thin entry point: parse args, call cli::run
├── cli/             command tree (clap) + interactive wizards + TUI
├── domain/          core data model: profiles, providers, proxies, routes
├── storage/         persistence of the domain model (embedded SQLite)
├── server/          OpenAI-compatible HTTP surface + auth + rate limiting
├── router/          model resolution, failover execution, routing state
├── health/          background probe loop for unhealthy entries
├── crypto/          secrets at rest (ChaCha20-Poly1305 + Argon2id)
├── adapter/         modular API adapters, master registry (ApiKind)
│   ├── inbound/     per-surface inbound: openai, anthropic, google
│   └── outbound/    per-provider outbound: openai, anthropic, google
├── translator/      canonical request/response model (no provider logic)
└── bin/
    └── gen-docs     developer-only: man pages, completions, CLI markdown
```

Each subsystem is isolated and testable. The CLI owns configuration and
administration; the server owns the runtime HTTP surface; the router owns
the failover logic; storage owns persistence.

## Data model

### Profile

A tenant in AGOS Proxy. A profile owns providers and proxies. Its opaque `id`
doubles as the bearer token that callers present against the HTTP API, so it is
generated by the CLI and treated like any other secret.

| Field            | Type   | Notes                                                      |
|------------------|--------|------------------------------------------------------------|
| `id`             | String | Opaque identifier, generated once; also the API token.     |
| `name`           | String | Human-readable label, e.g. `coder1`.                       |
| `description`    | Option | Free-text description.                                     |
| `password_hash`  | Option | Argon2id hash gating interactive management.               |
| `created_at`     | i64    | Unix timestamp.                                            |
| `updated_at`     | i64    | Unix timestamp.                                            |
| `rpm_limit`      | i64    | Requests-per-minute ceiling; 0 = unlimited.                |

### Provider

A configured upstream, belonging to a profile. This is *how* AGOS Proxy reaches
a model: the base URL to talk to and the credentials to present. The stored
token is encrypted at rest.

| Field          | Type      | Notes                                           |
|----------------|-----------|-------------------------------------------------|
| `id`           | i64       | Auto-increment primary key.                     |
| `profile_id`   | String    | Owning profile.                                 |
| `name`         | String    | Human label, e.g. `deepseek`.                   |
| `description`  | Option    | Free-text.                                      |
| `base_url`     | String    | Upstream base URL.                              |
| `auth_token`   | String    | Encrypted at rest; never returned in clear text.|
| `kind`         | ProviderKind | Determines the outbound adapter used.        |
| `extra_headers`| BTreeMap  | Non-standard headers sent with every request.   |

### ProviderKind

What wire format a provider speaks. AGOS Proxy uses this to pick the
outbound adapter that shapes requests and decodes responses.

| Variant              | Use case                                              |
|----------------------|-------------------------------------------------------|
| `OpenAICompatible`  | Most providers; request/response pass through.        |
| `Anthropic`         | Native `/v1/messages` translation.                    |
| `Google`            | Native Gemini `generateContent` translation.          |
| `Custom`            | Reserved for future native integrations.              |

### Proxy

A named group of routes a profile exposes, e.g. `Programmer`.

| Field          | Type   | Notes                                    |
|----------------|--------|------------------------------------------|
| `id`           | i64    | Auto-increment primary key.              |
| `profile_id`   | String | Owning profile.                          |
| `name`         | String | Human label.                             |
| `description`  | Option | Free-text.                               |

### Route

A single addressable target, e.g. `php-developer-3.5-flash`, owned by a proxy.
The name is what callers send as the OpenAI `model` string
(prefixed with the proxy, e.g. `Programmer/php-developer-3.5-flash`).

| Field          | Type            | Notes                                          |
|----------------|-----------------|------------------------------------------------|
| `id`           | i64             | Auto-increment primary key.                    |
| `proxy_id`     | i64             | Owning proxy.                                  |
| `name`         | String          | Route name.                                    |
| `description`  | Option          | Free-text.                                     |
| `strategy`     | RoutingStrategy | How the entry chain is picked from.            |

### RoutingStrategy

How an ordered chain of models is picked from.

| Variant       | Behavior                                                        |
|---------------|-----------------------------------------------------------------|
| `Priority`    | Strict pipeline order: entry 1, then 2, ... on failure.        |
| `RoundRobin`  | Distribute across currently-healthy entries round-robin.        |
| `Weighted`    | Like round robin, but biased by each entry's weight.           |

### RouteEntry

One rung of a route's fallback chain: a real model on one configured provider.

| Field          | Type            | Notes                                          |
|----------------|-----------------|------------------------------------------------|
| `id`           | i64             | Auto-increment primary key.                    |
| `route_id`     | i64             | Owning route.                                  |
| `provider_id`  | i64             | The configured provider used to reach this model.|
| `model_id`     | String          | The model string the provider expects.         |
| `priority`     | i32             | Order in the fallback chain; 1 is tried first. |
| `weight`       | f64             | Relative weight; used only when `Weighted`.    |
| `status`       | ModelStatus     | Current health state.                          |
| `capabilities` | RouteCapabilities | Feature flags for capability-aware routing.  |

### ModelStatus

Automated health state of a route entry.

| Variant      | Meaning                                                         |
|--------------|-----------------------------------------------------------------|
| `Healthy`    | In normal rotation; used for live traffic.                     |
| `Degraded`   | Failed or slow recently but still offered; demotes to Unhealthy|
| `Unhealthy`  | Skipped from live traffic; probed again in the background.     |
| `Disabled`   | Switched off manually by the user.                             |

### RouteCapabilities

Optional feature flags on a route entry, used to avoid routing a request to a
model that cannot actually serve it.

| Field         | Type   | Notes                                              |
|---------------|--------|----------------------------------------------------|
| `tools`       | bool   | Supports tool / function calling.                  |
| `vision`      | bool   | Supports image (vision) input.                     |
| `json_mode`   | bool   | Supports structured JSON output.                   |
| `max_context` | Option | Maximum context window in tokens; `None` if unknown.|

### UsageRecord

One logged request against a route entry: outcome, latency, and token use.
Written by the server on every completion attempt and surfaced through
`agos-proxy usage`.

| Field              | Type   | Notes                                          |
|--------------------|--------|------------------------------------------------|
| `id`               | i64    | Auto-increment primary key.                    |
| `profile_id`       | String | Owning profile.                                |
| `route_entry_id`   | i64    | The route entry that handled (or tried) this.  |
| `model_id`         | String | Model string used.                             |
| `streamed`         | bool   | Whether the request was streaming.             |
| `success`          | bool   | Whether the attempt succeeded.                 |
| `status_code`      | Option | HTTP status from the upstream, if any.         |
| `error_message`    | Option | Error text on failure.                         |
| `latency_ms`       | i64    | End-to-end latency for the attempt.           |
| `prompt_tokens`    | Option | Tokens in the prompt, if reported.            |
| `completion_tokens`| Option | Tokens in the response, if reported.          |
| `created_at`       | i64    | Unix timestamp.                                |

### UsageStats

Aggregate usage per model over a window: calls, failures, latency, tokens.

| Field              | Type   | Notes                                          |
|--------------------|--------|------------------------------------------------|
| `model_id`         | String | Model string.                                  |
| `calls`            | i64    | Total attempts.                                |
| `failures`         | i64    | Failed attempts.                               |
| `avg_latency_ms`   | f64    | Mean latency across attempts.                  |
| `prompt_tokens`    | i64    | Sum of prompt tokens.                          |
| `completion_tokens`| i64    | Sum of completion tokens.                      |

## Request lifecycle

1. A caller sends `POST /v1/chat/completions` with
   `Authorization: Bearer <profile_uid>` and
   `model: "Programmer/php-developer-3.5-flash"`.
2. The server authenticates the UID, resolves it to a profile, then resolves
   the `proxy/route` string to a route.
3. The route's model chain is filtered to healthy, enabled entries (and, when
   the request needs it, to entries with the required capabilities).
4. Models are tried in order. Each attempt has a configurable timeout.
5. On success: the response (or stream) is returned untouched; usage and latency
   are logged against that model.
6. On failure: that model is marked unhealthy and the next one is tried
   immediately — the caller perceives extra latency, not a failed request.
7. Only if the whole chain is exhausted does the route return an error.

## Health and circuit breaking

Each route entry has a status (`healthy` / `degraded` / `unhealthy` /
`disabled`). Failure conditions: connection failure, timeout, HTTP 5xx,
HTTP 429, or a response that fails schema validation. A background task probes
`unhealthy` entries on a backoff schedule and promotes them back to `healthy`
when they recover, automatically rejoining rotation.

The probe loop runs every 30 seconds. It pings each candidate entry with
`GET /v1/models` (cheap, fast, and works across every OpenAI-compatible
provider). The status machine:

```
Healthy ──────► Healthy   (always stays healthy; live-traffic failures
                           demote, not probes)

Degraded ──success──► Healthy
         ──failure──► Unhealthy

Unhealthy ─success──► Degraded   (must prove itself once before full promotion)
          ──failure──► Unhealthy

Disabled ──────────► Disabled    (never probed)
```

## Routing strategies

- **Priority** (default): strict pipeline order; fallback on failure.
- **Round robin**: spread traffic across all healthy entries.
- **Weighted**: like round robin, but biased by each entry's weight.

Resolution is scoped to the caller's profile. A route name is meaningful only
within its owning proxy and profile — there is no cross-profile leakage.

## Streaming

Responses are passed through as a live SSE stream. As with any gateway there is
a documented limitation: if a stream fails *after* tokens have begun flowing,
that partial failure is logged distinctly because it cannot be invisibly retried.

For non-streaming requests, the full response body is read before returning,
so failover is transparent end-to-end.

## Security

- Provider `auth_token` values are encrypted at rest (never in plaintext files).
- The profile UID acts as the bearer token — treated like any API key.
- A profile may be password-gated for interactive management.
- Token rotation is supported per profile.
- Secrets are encrypted with ChaCha20-Poly1305; the master key is randomly
  generated and stored in the store's `meta` table.
- Optional profile passwords are hashed with Argon2id (random salt).

## Tech stack

- **Runtime:** `tokio`
- **HTTP server / proxy:** `axum` (streams response bodies natively, which
  matters for SSE passthrough).
- **Outbound provider calls:** `reqwest` (async, streaming-capable).
- **Storage:** embedded SQLite (single file, no external DB).
- **Serialization:** `serde` / `serde_json`.
- **Secrets:** ChaCha20-Poly1305 at rest, key derived via argon2 from an
  optional profile password.
- **CLI:** `clap` for flags, `dialoguer` for interactive wizards,
  `ratatui` + `crossterm` for the full-screen chat UI.
- **Documentation generation:** `clap-markdown`, `clap_mangen`, `clap_complete`
  (optional `gen-docs` feature).

## Build phases

### MVP (current)

- Single and multi-profile support.
- Provider CRUD with encrypted secrets.
- Proxy and route CRUD.
- Priority, round-robin, and weighted routing strategies.
- Automatic failover with health tracking and background recovery.
- `/v1/chat/completions` (streaming and non-streaming).
- `/v1/completions` and `/v1/embeddings` passthrough.
- `/v1/models` auto-listing from configured routes.
- Bearer token auth + per-profile rate limiting.
- Interactive CLI wizards + non-interactive flags.
- Full-screen TUI chat.
- Config export/import with passphrase sealing.
- Usage logging and per-model aggregates.
- Docker test environment with mock upstream.

### V2 (planned)

- Capability-aware routing (already partially implemented — route entry
  capabilities are stored and `RequestNeeds` is derived from the body; the
  router filters entries accordingly).
- Cost tracking per model and per route.
- Failover webhooks.
- Richer CLI stats and history search.
- Provider-specific advanced options (temperature cloning, seed, top_p, etc.).

## Storage schema

The store is a single SQLite file using WAL journal mode and foreign keys.
Tables:

- `profiles` — profile rows.
- `providers` — upstream providers (auth_token stored as encrypted blob).
- `proxies` — named route groups.
- `routes` — addressable fallback chains.
- `route_entries` — individual model rungs within a chain.
- `usage_log` — per-request attempt records.
- `meta` — store-level metadata (e.g. the master key).

Migrations are applied idempotently on store open. Column additions are checked
and applied one at a time via `ensure_column`, so existing stores are brought
up to date without data loss.

## Module responsibilities

| Module        | Owns                                                                    |
|---------------|-------------------------------------------------------------------------|
| `domain`      | Pure data types; no I/O, no side effects.                              |
| `storage`     | SQLite persistence, CRUD, usage queries, encrypted token round-trip.   |
| `crypto`      | Master key, encrypt/decrypt, Argon2id derivation, password hashing.    |
| `cli`         | Command parsing, wizards, TUI, bootstrap, config export/import.        |
| `server`      | HTTP surface, auth middleware, rate limiter, handler dispatch.          |
| `router`      | Model resolution, strategy application, failover execution, logging.    |
| `health`      | Background probe loop, status machine, entry recovery.                  |
| `adapter`     | Master adapter registry; inbound per-surface + outbound per-provider.   |
| `translator`  | Canonical request/response/stream types shared by all adapters.         |

## Testing strategy

- **Unit tests** are inline in each module (`#[cfg(test)]`), covering the
  domain logic, crypto round-trips, routing resolution, rate limiter, and
  password hashing.
- **Integration-style tests** in `cli/chat.rs` and `cli/tui.rs` spin up a
  real mock upstream and exercise the full routing path.
- **E2E tests** live in `tests/e2e_test.rs` and exercise the server against
  a real HTTP caller.
